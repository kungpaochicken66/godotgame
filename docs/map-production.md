## Spend director time where it changes play

The builder fixes obvious defects first, captures a short actual-play clip or a few matched-camera frames covering the first controllable frame, signature action and visible outcome, identifies the build and notes any untested route. At Fable's review points, send Fable (in English via the designated sender, with evidence accessible on EC2) just the brief and representative evidence; do not resend full or unrelated logs. Ask for up to three concrete shortcomings, each with the moment, the problem for the child, and how to tell that it improved. The implementation owner makes the repairs. When a creative question remains, return the same matched camera, action, outcome and language for a short follow-up. Under the relative-polish handoff rule, stop once the episode is polished for its scope with no obvious weakness and the affected checks pass, then freeze the candidate for Mac target-specific acceptance. A technical failure stays with the builder.

## Evaluate a playable milestone

Use one row in the existing task record per comparable work item. Include the task type and scope, baseline, actual observed model/effort, workflow revision, candidate, reviewer and host-local evidence link. Record file availability, acknowledgment, verification and acceptance as separate facts, and record the outcome after independent verification. An unstarted task is pending; count only reviewed attempts in rates.

| What to measure | How to record it |
| --- | --- |
| Playability | Pass, fail or untested for normal entry, signature action, visible consequence and return. Include save/revisit and two clients where applicable. A failed required check blocks acceptance. |
| Player experience | From the game camera, rate each of story identity, action and consequence, and legibility of the goal or earned discovery. Use 0 for missing or misleading, 1 for understandable with a hint, 2 for clear in play. Attach a timestamp or frame for weak points. Label reviewer judgement separately from observations of a child playing. |
| Reliability by task type | Record first-pass acceptances / independently reviewed items, repair rounds and defects discovered after acceptance. Show counts alongside rates for small samples. |
| Cost of getting it right | Record model work (builder and review work, Fable calls/tokens and other actual model usage when available), repair time, delivery/transport waits and machine (or quota) waits as separate measured fields. Mark unavailable measurements as unknown. |
| Reuse | Link a second map that actually used the component or method, and the work it avoided. Until then, record it as a candidate for reuse. |

Use Odyssey's playable voyage and journal as references for how the child's action reads. Compare like milestones at similar scope. Keep individual dimensions visible; a cheap run or an attractive shot cannot offset a broken route.

## Improve model assignments from real runs

1. Start with a narrow task whose expected result is observable. Rule fixtures, known-format asset conversion, locale coverage and connecting an existing discovery event are good trials. Novel story direction and judgements about timing or composition stay with Fable. For a Mac assignment the desk checks quota and machine capacity before execution. Fable selects work and checks capacity on EC2.
2. Give one available model the task with a baseline, write scope and acceptance example. On Mac, new and resumed local AGY building and verification use AGY Orchestrator (Neon) (`gemini-pro-orchestrator-neon`, high effort), verified on actual work and kept distinct from plain Neon High (`gemini-4-neon-high`). An independent reviewer checks the frozen result using the Mac verification assignment above where applicable. Record failures and rework as well as passes.
3. Compare the result with recent comparable work. If quality holds across repeated real examples and verification plus rework uses fewer scarce resources, make that model the first choice for **that task type**. If defects escape or repeated repairs erase the saving, narrow or reassign the task. With too little evidence, continue the trial without claiming a saving.
4. Change one routing or review practice at a time where practical. Use [Recording improvements](mac-ec2-agent-workflow.md#recording-improvements) to place each trial in the playbook, skill or check where it runs. Record the expected benefit and criteria for retiring it. When adopting a change, link the versioned record from the queue. The Mac workflow owner turns cross-host decisions into executable local work for Neon to schedule.

## Two messages the desk can reuse

**Creative brief request** — “Seed: [one or two sentences]. Audience and series: [reference]. Design the first playable episode. What will the child do that could only happen in this story? Describe the approach, the moment it changes, the reward and what the child can revisit. Name the existing UI or journal elements worth reusing. Leave room for the builder to solve implementation details.”

**Gameplay review request** — “Here is [revision], the intended moment, and a short matched-camera capture (first controllable frame, action and outcome). Where would the child miss a cue, lose the subject, or fail to notice the effect of their action? Give up to three timestamped changes with an observable success condition. On the next review, compare the matched shots and identify what still matters.”

Record the response and resulting decision in the title's existing notes beside its code. Keep cycle notes short enough for the next title to reuse them without replaying a long conversation.

For applicable trial implementation with a visible cue or camera change, keep the English game camera iteration skill (Mac production branch `codex/mac-neon-workflow-1436z`, path `tools/map-production/skills/game-camera-iteration/SKILL.md`) in scope and keep Godot MCP disabled, as defined in the controlled camera trial on that branch (`docs/game-camera-trial.md`), so the two are evaluated separately. Ask the builder to inspect the original and resulting player-camera frames at the first playable milestone.
